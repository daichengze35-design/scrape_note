Web API 加密逻辑分析
    第 4 阶段：密码学基础

    学习目标
        能从安全目标、输入、输出、密钥关系和必要参数五个方面描述密码学机制
        能区分哈希、校验和、MAC、HMAC、对称加密、认证加密、非对称加密和数字签名
        能准确说明 key、salt、IV、nonce、counter、tag、digest、signature 和 AAD 的不同作用
        能说明 AES 的分组大小、密钥大小、工作模式和填充之间的关系
        能说明 RSA 加密方案、RSA 签名方案和密钥长度不是同一个参数
        能说明密钥交换、KDF 和密码派生分别解决什么问题
        能说明 Web Crypto 与 CryptoJS 是接口或库，不是单一算法
        能根据字段位置、字节长度、调用参数和密钥关系形成候选分类，但不凭外观确认算法
        能把稳定标准事实、实现相关事实、推断和未知分开记录

    本阶段不学习
        不提供真实站点、靶场、练习或实战任务
        不编写可执行的哈希、HMAC、AES、RSA、签名或解密代码
        不复现、修改、重放或伪造任何请求
        不提取、猜测、暴力搜索或传播密钥、Token、Cookie、密码或其他秘密
        不使用 Web Crypto 或 CryptoJS 调用真实接口
        不定位具体站点的签名函数、密钥来源或加密入口
        不处理 webpack、Vite、混淆、Worker、Service Worker 或 WASM 内部实现
        不绕过认证、授权、验证码、风控、付费限制或 DRM
        不把密码学知识用于未授权数据恢复或保护绕过

    标准与版本状态
        密码学标准、算法批准状态和库支持范围会更新
        本阶段使用长期稳定的原语定义和输入输出关系
        不把“某浏览器提供”“某库可以调用”写成“该算法适合新系统”
        不根据旧教程中的默认参数决定新实现
        实际设计或实现前需要重新核对当时有效的一手标准与库文档
        需要核对的标准标识包括
            FIPS 197：AES
            FIPS 180 系列：安全哈希标准
            FIPS 198 系列及其后续文件：HMAC
            NIST SP 800-38A：分组密码工作模式
            NIST SP 800-38D：GCM 与 GMAC
            FIPS 186 系列：数字签名
            RFC 2104：HMAC
            RFC 5869：HKDF
            RFC 8017：RSA 密码学规范
            RFC 9106：Argon2
        编写状态
            本阶段编写时无法连接 NIST 与 RFC Editor 在线页面
            因此不声明这些文件在当前日期的批准、撤销或修订状态
            本阶段不引用依赖当前政策状态的算法推荐结论
        独立核对补充
            独立只读审查成功访问了 FIPS 197 与 FIPS 186-5 的 NIST 官方页面
            FIPS 197 官方页面说明 2023 年更新未改变 AES 的技术内容
            FIPS 186-5 官方页面确认其数字签名标准标识
            其他列出文件的当前修订与生命周期状态仍未完成在线核验
            因此上面的标准状态限制仍然适用

    密码学机制的五项记录
        安全目标
            该机制要提供保密性、完整性、来源认证、公开验证、密钥建立还是密码派生
        输入
            实际进入算法的字节、密钥和参数
        输出
            摘要、认证标签、密文、签名、共享秘密或派生密钥
        密钥关系
            不使用密钥、使用共享秘密，还是使用公钥与私钥
        必要参数
            算法名称之外还需要的模式、IV、nonce、salt、counter、tag 长度、padding 或上下文
        分类要求
            五项中存在未知时应明确保留未知
            只知道算法名称而不知道模式和参数，通常不足以描述完整机制

    主要安全目标
        保密性
            使没有相应解密能力的一方不能获得受保护内容
            对称加密和公钥加密可以用于提供保密性
        完整性
            使接收方能够检测受保护数据是否被改变
            哈希本身只能提供比对值，不能在有主动攻击者时独立证明完整性
            MAC、数字签名和认证加密可以在各自密钥模型下提供完整性验证
        来源认证
            验证消息来自掌握相应认证密钥的一方
            MAC 验证证明发送方掌握共享秘密
            数字签名验证证明签名由对应私钥产生，但身份还取决于公钥怎样绑定到主体
        公开验证
            不持有签名私钥的一方可以使用公钥验证数字签名
            MAC 验证方持有共享秘密，通常也具备生成合法 MAC 的能力
        新鲜性
            判断消息是否属于允许的时间窗口或是否已经使用过
            哈希、MAC、加密和数字签名都不会自动提供新鲜性
            新鲜性通常还需要 timestamp、nonce、序号和服务端状态
        不直接提供的目标
            密码学验证成功不自动代表业务授权通过
            加密不自动提供可用性
            数字签名不自动形成法律或业务层面的不可否认性

    密码学输入是字节
        文本进入算法前必须变成字节
        同一可见文本可能具有不同字节表示
        可能改变字节的因素
            UTF-8、UTF-16 或其他字符编码
            Unicode 规范化形式
            换行是 LF 还是 CRLF
            是否保留前导或尾随空格
            JSON 字段顺序、空白和转义方式
            数字、布尔值和 null 的文本表示
            URL 编码和表单编码规则
            Base64、Base64url 与 Hex 的解码时机
        记录原则
            “业务字段相同”不等于“算法输入字节相同”
            不知道编码和序列化规则时，不能确认摘要、MAC、签名或密文为何不同
            第 5 阶段再具体分析签名输入的规范化与拼接顺序

    符号化表达
        目的
            用抽象关系区分机制，不表示某个库的真实函数语法
        哈希
            digest = Hash(message_bytes)
        MAC
            tag = MAC(secret_key, message_bytes)
        对称加密
            ciphertext = Encrypt(secret_key, parameters, plaintext_bytes)
        认证加密
            ciphertext_and_tag = AEAD_Encrypt(secret_key, nonce, plaintext_bytes, AAD)
        公钥加密
            ciphertext = PublicKeyEncrypt(public_key, scheme, plaintext_bytes)
        数字签名
            signature = Sign(private_key, scheme, message_bytes)
        验证
            verification_result = Verify(key, scheme, message_bytes, tag_or_signature)
        重点
            这些表达只说明输入输出类别
            实际方案还可能内部执行哈希、编码、填充和密钥派生

    确定性与随机化
        确定性机制
            相同算法、相同输入字节和相同必要参数会产生相同输出
            普通哈希通常是确定性的
            HMAC 在相同密钥和相同消息下通常是确定性的
        随机化或唯一参数机制
            加密方案通常还使用随机值、唯一 nonce、IV 或内部随机化
            同一明文在不同参数下可以产生不同密文
            数字签名是否每次相同取决于具体签名方案和参数生成方式
        观察限制
            两次输出相同不能单独证明是哈希或 HMAC
            两次输出不同不能单独证明是加密
            时间戳、随机数、salt、nonce、序列化和隐藏状态都可能改变输出

    哈希函数
        输入
            在算法规定范围内的可变长度字节串
        输出
            由算法规定长度的摘要
        密钥
            普通密码学哈希函数不使用秘密密钥
        主要性质
            相同输入产生相同摘要
            输入发生变化时，摘要通常发生大范围变化
            摘要长度通常与输入长度无关
        不提供
            不提供保密性
            不提供发送方身份认证
            不自动提供重放防护
            不允许通过“解密”恢复原文

    哈希安全性质
        原像抗性
            给定一个摘要，寻找任意输入使其产生该摘要应在计算上不可行
        第二原像抗性
            给定一个具体输入，寻找另一个不同输入产生相同摘要应在计算上不可行
        碰撞抗性
            寻找任意两个不同输入产生同一摘要应在计算上不可行
        三者区别
            原像问题从摘要出发
            第二原像问题固定其中一个输入
            碰撞问题可以自由选择两个输入
        有限输出
            哈希输出空间有限而输入空间更大，因此数学上必然存在碰撞
            安全要求不是“绝对没有碰撞”，而是寻找碰撞在计算上不可行

    常见哈希名称与输出长度
        MD5
            摘要长度为 128 bit，也就是 16 byte
            Hex 表示通常为 32 个字符
            已知存在实用碰撞攻击，不能仅因旧系统仍使用就推断其满足现代碰撞安全要求
        SHA-1
            摘要长度为 160 bit，也就是 20 byte
            Hex 表示通常为 40 个字符
            已知存在实用碰撞攻击，不能用于需要可靠碰撞抗性的推断
        SHA-256
            摘要长度为 256 bit，也就是 32 byte
            Hex 表示通常为 64 个字符
        SHA-384
            摘要长度为 384 bit，也就是 48 byte
            Hex 表示通常为 96 个字符
        SHA-512
            摘要长度为 512 bit，也就是 64 byte
            Hex 表示通常为 128 个字符
        长度限制
            相同长度的字段可能来自截断、随机值、密文片段或其他算法
            输出长度只能用于排除不匹配候选，不能单独确认算法

    摘要的文本表示
        原始摘要是字节
        Hex 表示
            一个摘要字节表示为两个 Hex 字符
            字母大小写不改变解码后的字节，但会改变文本本身
        Base64 表示
            文本长度受字节数和补位规则影响
            Base64url 使用不同字符表，并可能省略 = 补位
        判断顺序
            先确认外层文本编码
            再计算解码后的字节长度
            最后才能与候选摘要长度比较

    校验和与密码学哈希
        校验和
            常用于检测传输或存储中的偶然错误
            CRC 是常见校验机制类别
            一般不以抵抗主动构造碰撞为设计目标
        密码学哈希
            以原像、第二原像和碰撞等密码学性质为设计目标
        共同点
            都可以把输入映射为较短的固定或有限长度值
        不能混用
            校验和匹配不能在主动攻击者模型下证明消息真实
            普通哈希匹配也不能证明发送方掌握秘密

    哈希与密码
        密码通常来自低熵、可预测的人类输入
        直接使用 MD5、SHA-1、SHA-256 或 SHA-512 处理密码通常速度过快
        快速哈希会使离线猜测成本过低
        密码存储或密码派生通常需要专门的密码处理机制
        必要组成可能包括
            每个记录独立的 salt
            可调工作因子
            内存成本
            并行度参数
        不能根据字段名 passwordHash 认定实现正确

    MAC
        全称
            Message Authentication Code
        输入
            共享秘密密钥
            消息字节
            具体 MAC 算法要求的参数
        输出
            认证标签 tag
        提供
            消息完整性验证
            发送方掌握共享秘密的认证
        不提供
            不隐藏消息内容
            不自动阻止合法消息被重放
            不提供公钥式公开验证
        密钥模型
            生成方和验证方都需要掌握共享秘密或等价认证能力
            因此验证方通常也能生成合法标签

    HMAC
        概念
            HMAC 是基于密码学哈希函数构造的 MAC
        完整算法名称
            HMAC-SHA-256 表示 HMAC 构造使用 SHA-256
            HMAC-SHA-512 表示 HMAC 构造使用 SHA-512
        输入
            secret key
            message bytes
            underlying hash function
        输出
            认证标签
            完整输出长度通常与底层哈希输出长度相关
            协议也可能按明确规则截断标签
        确定性
            相同密钥、相同消息字节、相同哈希和相同截断规则产生相同标签
        与普通哈希的区别
            HMAC 必须有密钥参与
            SHA-256(message) 不等于 HMAC-SHA-256(key, message)
            把 secret 与 message 简单拼接后哈希不自动等于 HMAC

    MAC 标签截断
        协议可以定义只传输完整 MAC 的一部分
        截断会改变字段长度和伪造概率
        安全性取决于保留长度、尝试次数限制和协议设计
        观察到短标签时需要记录
            完整算法候选
            实际传输字节数
            截取方向
            文本编码
        不能因为长度不是完整 SHA 输出就排除 HMAC

    MAC 验证
        验证方需要使用完全相同的消息字节和参数重新验证
        任一差异都可能造成验证失败
            字段顺序
            空格和换行
            字符编码
            URL 编码
            时间戳和 nonce
            标签截断位置
        标签比较应避免通过比较耗时泄露匹配前缀
        错误响应不应区分出过多内部验证细节
        本阶段只理解要求，不实现比较逻辑

    MAC、签名与重放
        合法 MAC 或数字签名可以在不同时间再次随原消息出现
        如果协议没有新鲜性验证，密码学验证仍可能通过
        参与重放防护的常见数据
            timestamp
            nonce
            sequence number
            request identifier
            服务端已使用值集合
        有这些字段不等于已经防重放
        必须确认字段被认证，并且服务端实际校验时间窗口或唯一性

    对称加密
        密钥模型
            加密方和解密方使用同一秘密，或使用可直接等价推导的秘密
        输入
            plaintext bytes
            secret key
            algorithm and mode parameters
        输出
            ciphertext bytes
            某些模式还输出认证标签
        主要目标
            保护明文的保密性
        限制
            只有保密性而没有认证的加密方案可能允许密文被修改
            对称加密不自动证明是哪个业务主体产生了消息

    分组密码
        概念
            分组密码在一个密钥下处理固定大小的数据分组
        多分组消息
            需要工作模式定义怎样处理超过一个分组的输入
            模式还会规定 IV、nonce、counter、padding 或 tag 的要求
        重点
            算法名称和工作模式必须分开记录
            只写 AES 通常不足以描述实际加密机制

    流密码与密钥流
        流密码或流式模式会生成与消息结合的密钥流
        同一密钥流不能安全地重复用于不同明文
        nonce 或 counter 常用于确保密钥流不重复
        流式处理通常不要求把明文补齐到分组大小
        “输出长度接近输入长度”不能单独证明使用了流密码

    AES
        全称
            Advanced Encryption Standard
        类型
            AES 是对称分组密码
        分组大小
            AES 分组大小固定为 128 bit，也就是 16 byte
        标准密钥大小
            128 bit
            192 bit
            256 bit
        名称解释
            AES-128、AES-192、AES-256 中的数字表示密钥大小
            它们的分组大小都仍是 128 bit
        不能由 AES 名称确定
            工作模式
            IV 或 nonce 规则
            padding 规则
            tag 长度
            输出封装格式

    工作模式
        作用
            定义分组密码怎样处理一个或多个分组
        常见名称
            ECB
            CBC
            CTR
            GCM
        模式差异
            是否需要 IV 或 nonce
            参数要求唯一还是不可预测
            是否需要 padding
            是否提供认证标签
            密文长度怎样形成
        记录要求
            不把库的默认模式当成协议事实
            必须从调用参数、规范或可验证行为确认模式

    ECB
        全称
            Electronic Codebook
        参数
            不使用 IV
        主要特征
            在同一密钥下，相同明文分组产生相同密文分组
            多个分组分别处理，无法隐藏重复分组关系
        安全边界
            ECB 不提供消息认证
            对结构化多分组数据不能提供语义安全的保密性
        识别限制
            看到重复密文分组可以形成 ECB 候选
            没看到重复分组不能排除 ECB，因为明文分组本身可能不重复

    CBC
        全称
            Cipher Block Chaining
        IV
            CBC 使用一个分组大小的 IV
            对 AES-CBC，IV 长度是 16 byte
            加密时的 IV 通常需要在同一密钥下不可预测
            IV 不需要作为密钥保密，但必须按协议完整传给解密方
        CBC IV 要求修正
            上面的“通常需要”是概括性表述
            按 NIST SP 800-38A 的 CBC 加密要求，IV 必须不可预测
            IV 不需要保密，但其完整性应受到保护
            解密方除了取得同一 IV，还需要防止 IV 在未被检测的情况下遭到修改
        padding
            CBC 处理的输入需要形成完整分组
            非整分组明文通常使用明确 padding 规则补齐
        安全边界
            CBC 本身不提供消息认证
            未认证 CBC 的密文可能被修改而不在解密前被可靠检测
            可区分的 padding 错误可能形成 padding oracle 风险
        观察限制
            密文长度为 16 byte 的倍数只是 CBC 等分组模式的弱线索
            IV、密文、tag 和外层编码的组合会改变字段总长度

    padding
        作用
            把输入补到算法或编码方案要求的长度
        分组填充
            用于 CBC 等需要完整分组的模式
            PKCS#7 是常见分组填充规则名称
        PKCS#7 基本关系
            需要补 p 个字节时，每个填充值都表示 p
            明文已经对齐时仍会增加一个完整填充分组
            解密后必须验证并移除合法填充
        名称差异
            一些库会用 PKCS5Padding 名称表示与分组大小相适配的同类填充行为
            不能只根据显示名称判断真实字节规则
        其他 padding
            RSA 加密和签名方案中的编码或 padding 与分组填充不是同一机制
            Base64 的 = 也不是密码学分组填充

    CTR
        全称
            Counter Mode
        作用
            使用分组密码加密一系列 counter block 形成密钥流
            明文与密钥流结合得到密文
        参数
            counter 的初始值和递增规则属于协议参数
            同一密钥下使用的 counter block 不能重复
        特点
            不需要 PKCS#7 分组填充
            密文主体长度通常与明文长度相同
        安全边界
            CTR 本身不提供消息认证
            重复使用相同密钥流会泄露不同明文之间的关系
        名称限制
            某些接口把 nonce 和 counter 的不同部分合并在一个计数器块中
            必须记录整个 counter block 布局，不能只记录一个字段名

    认证加密
        目标
            同时提供保密性和密文完整性验证
        AEAD
            Authenticated Encryption with Associated Data
            同时处理 plaintext 和可选 AAD
            输出通常包含 ciphertext 与 authentication tag
        解密结果
            只有标签验证成功时，明文才应被接受
            标签失败表示密钥、nonce、AAD、密文、tag 或参数至少有一项不匹配
        不能推断
            标签失败不能单独指出是哪一项错误
            有 tag 字段也不能只凭字段名确认使用了 AEAD

    GCM
        全称
            Galois/Counter Mode
        类型
            GCM 是分组密码的认证加密模式
            AES-GCM 是常见组合名称
        输入
            key
            nonce 或 IV
            plaintext
            可选 AAD
            tag length 等方案参数
        输出
            ciphertext
            authentication tag
        长度关系
            GCM 密文主体长度通常与明文字节长度相同
            tag 可以单独保存，也可以与密文拼接
            外层封装还可能加入 nonce、版本和 key identifier
        nonce 要求
            同一密钥下 nonce 必须满足方案的唯一性要求
            随机生成是实现唯一性的方式之一，但随机不等于绝对不会重复
            计数器也可以在受控范围内提供唯一性
        安全边界
            同一密钥重复使用 nonce 会严重破坏安全性
            tag 截断规则和允许尝试次数会影响认证强度

    AAD
        全称
            Additional Authenticated Data
        作用
            AAD 参与认证标签计算
            AAD 不作为密文被加密
        常见内容类别
            协议版本
            消息类型
            不需要保密但必须防止修改的头部
        验证要求
            加密和解密时 AAD 字节必须一致
            字段含义相同但序列化字节不同仍会造成验证失败
        观察限制
            AAD 可能不随密文一起存储
            只观察密文字段时可能无法知道 AAD 来源

    key
        作用
            决定密码学变换或验证能力
        秘密性
            对称密钥、MAC 密钥和私钥通常需要保密
            公钥不要求保密
        key identifier
            key id 只用于选择密钥
            key id 不是密钥本身
        长度
            密钥的 bit 长度是解码后的密钥材料或算法参数
            Base64 或 Hex 文本长度不是直接的 key bit 长度
        记录要求
            只记录密钥类型、来源类别、长度和用途
            不在教程证据中记录真实密钥值

    IV
        全称
            Initialization Vector
        作用
            使同一密钥下的加密状态按方案要求变化
        要求依赖模式
            CBC 重点要求不可预测
            GCM 重点要求同一密钥下唯一
            不同模式不能共用一句“IV 必须随机”概括全部要求
        秘密性
            IV 通常不需要保密
            IV 公开不等于可以重复或任意选择
        位置
            可以单独字段传输
            可以放在密文前部
            可以由协议上下文推导

    nonce
        含义
            nonce 表示在规定范围内只使用一次的值
        主要要求
            具体方案可能要求唯一、不可预测，或同时有其他结构要求
        生成方式
            随机值
            计数器
            发送方标识与计数器组合
            协议定义的其他唯一结构
        秘密性
            nonce 通常不需要保密
        易混淆点
            timestamp 不是天然唯一的 nonce
            requestId 不一定参与密码学处理
            字段名 nonce 不证明服务端验证了唯一性

    counter
        counter 是按协议规则变化的计数值或计数器块
        可用于 CTR 密钥流生成、消息排序或新鲜性控制
        counter 是否从零开始、占多少 bit、怎样递增都属于必要参数
        counter 回绕或重复可能导致同一密钥下输入重复
        业务 sequence number 与密码学 counter 可能有关，也可能完全无关

    salt
        作用
            salt 为密钥派生或密码处理提供每个实例不同的公开输入
        秘密性
            salt 通常不需要保密
        主要目标
            避免相同低熵输入在不同记录中产生相同派生结果
            增加预计算结果跨记录复用的成本
        要求
            通常需要在相应作用域内唯一或具有足够低的碰撞概率
            长度和生成方式由方案规定
        不提供
            salt 不替代密码或密钥
            salt 不等于 IV
            salt 不单独阻止针对某一个密码记录的猜测

    tag
        tag 是认证机制输出的标签
        可能来自 MAC 或 AEAD
        tag 通常不需要保密
        tag 长度和编码属于协议参数
        tag 验证失败时不能接受消息
        字段名 tag 也可能只是业务标签，因此仍需调用与参数证据

    digest
        digest 通常指哈希函数输出的摘要
        digest 不使用普通哈希之外的密钥时，不能提供发送方认证
        摘要可以作为签名或其他方案的内部输入
        传输字段可能保存完整摘要、截断摘要或摘要的文本编码

    signature
        signature 在业务字段中只是名称
        它可能表示
            数字签名
            HMAC 或其他 MAC
            普通哈希
            自定义校验字段
        只有密钥关系和验证方式能够区分密码学类别
        不能根据 sign、sig、signature 字段名直接写“数字签名”

    pepper
        pepper 是某些密码处理系统额外使用的秘密值
        pepper 与公开 salt 不同
        pepper 的存储和轮换属于密钥管理问题
        pepper 不是所有密码派生方案的标准必需参数
        观察到额外秘密时也不能自动把它命名为 pepper

    非对称密码学
        密钥模型
            使用关联的公钥和私钥
        公钥
            可以分发给验证方或加密方
        私钥
            由持有方保密
        主要用途类别
            公钥加密
            数字签名
            密钥协商或密钥封装
        重要限制
            不是每个非对称算法都同时支持所有用途
            不能把公钥和私钥简单理解为可任意互换的同一种密码

    RSA
        组成
            RSA 使用包含模数和指数等参数的公钥与私钥
        key size
            RSA key size 通常指模数的 bit 长度
        原始 RSA 运算
            只有数学运算而没有安全编码方案不足以形成安全加密或签名方案
        完整方案名称
            RSA-OAEP 属于 RSA 加密方案
            RSA-PSS 属于 RSA 签名方案
            PKCS#1 v1.5 名称可能指加密编码或签名编码，需要结合用途区分
        长度关系
            RSA 密文或签名的原始长度通常与模数字节长度相关
            外层 Base64 或 Hex 会改变可见文本长度
        识别限制
            相同长度可能来自 RSA 密文或 RSA 签名
            只写 RSA 不能说明是加密、签名、OAEP、PSS 还是其他方案

    RSA 加密输入限制
        RSA 加密方案不能直接加密任意长度消息
        最大明文长度受模数大小和编码方案开销限制
        OAEP 还依赖哈希函数和可选 label 等参数
        长数据通常使用混合加密
        不能通过把消息分块后逐块做原始 RSA 运算代替标准混合方案

    RSA 签名不是私钥加密
        数字签名方案具有独立的消息编码、哈希和验证规则
        把 RSA 签名称为“用私钥加密消息”会遗漏这些必要规则
        公钥验证签名也不是普通意义的“用公钥解密”
        记录时应使用 Sign 和 Verify，而不是 Encrypt 和 Decrypt

    混合加密
        目的
            结合对称加密处理大量数据的能力与非对称密钥建立能力
        典型组成
            生成临时对称内容密钥
            使用认证加密保护数据
            使用公钥方案封装或保护内容密钥
            把版本、nonce、封装密钥、密文和 tag 放入协议结构
        变化
            具体方案可能使用密钥封装机制、密钥协商或其他标准结构
        判断限制
            看到一个 RSA 字段和一个 AES 字段不证明二者形成正确混合方案
            必须确认密钥和数据之间的实际关系

    数字签名
        输入
            private key
            message bytes 或方案规定的摘要
            signature scheme parameters
        输出
            signature
        验证
            使用对应 public key 和相同消息进行验证
        提供
            消息完整性验证
            私钥持有证明
            公钥可验证性
        不提供
            不隐藏消息内容
            不自动证明公钥属于某个真实身份
            不自动阻止重放
            不自动授予业务权限

    数字签名中的哈希
        许多签名方案内部处理消息摘要
        有些接口接收原消息并内部哈希
        有些协议或接口接收预先计算的摘要
        两种调用方式不能混用
        重复哈希或漏掉所需哈希都会改变验证结果
        必须记录
            接口接收原消息还是摘要
            使用的哈希算法
            摘要是否包含算法标识或其他编码结构

    签名随机性与编码
        不同签名方案的随机化规则不同
        同一消息和同一私钥的签名
            可能每次不同
            也可能由确定性规则得到相同结果
        签名表示也会改变可见长度
            原始固定字段拼接
            DER 等结构化编码
            Base64 或 Base64url
        不能把“每次相同”或“每次不同”当成数字签名的通用判据

    MAC 与数字签名的区别
        MAC
            生成和验证依赖共享秘密
            验证方通常也能生成标签
            不提供独立第三方公开验证
        数字签名
            私钥生成签名
            公钥验证签名
            验证方不需要掌握私钥
        共同点
            都可以验证消息完整性和相应密钥持有关系
            都不自动提供保密性或重放防护
        API 字段
            业务上都可能被命名为 sign
            必须根据密钥关系分类

    椭圆曲线用途边界
        ECDSA
            是数字签名方案类别
            签名常包含 r 和 s 两个整数
            原始拼接与 DER 编码会产生不同字节表示
        ECDH
            是椭圆曲线密钥协商方案类别
            输出用于形成共享秘密材料
            ECDH 本身不是数字签名
        名称限制
            看到 EC key 不能直接判断用于签名还是密钥协商
            曲线、点编码、哈希、KDF 和输出格式都需要单独记录

    密钥交换与密钥协商
        目标
            让通信双方建立共享秘密材料
        Diffie-Hellman 类机制
            双方使用各自私有值和对方公开值计算相关共享结果
            ECDH 是椭圆曲线形式的密钥协商
        不直接提供
            共享结果通常还需要 KDF 才成为具体用途密钥
            未经认证的密钥协商不自动验证对方身份
            密钥协商本身不等于消息加密
        认证关系
            协议需要签名、证书、预共享密钥或其他机制绑定参与方身份

    KDF
        全称
            Key Derivation Function
        输入类别
            共享秘密
            主密钥
            密码
            salt
            context 或 info
        输出
            一个或多个规定长度的派生密钥
        作用
            把输入密钥材料转换为适合具体用途的密钥
            为不同用途建立密钥分离
        限制
            KDF 不能增加低熵密码本身包含的信息量
            不同 KDF 面向的输入模型和威胁不同

    HKDF
        类别
            HKDF 是基于 HMAC 的 KDF
        两个逻辑阶段
            Extract 把输入密钥材料处理为固定形式的伪随机密钥
            Expand 根据 info 和所需长度派生输出密钥材料
        salt
            HKDF 接口可以定义可选 salt 行为
            salt 不需要保密
            是否缺省以及缺省值怎样处理必须按具体规范记录
        info
            info 用于绑定协议、版本、方向或密钥用途等上下文
            info 通常不需要保密
        重点
            HKDF 不是用于降低人类密码猜测速度的内存困难密码哈希

    密码派生与密码哈希
        输入特点
            人类密码通常低熵且分布不均匀
        目标
            增加每次猜测的计算或内存成本
            使用独立 salt 阻止预计算跨记录复用
        常见方案类别
            PBKDF2
            scrypt
            Argon2
            bcrypt
        参数
            迭代次数或时间成本
            内存成本
            并行度
            输出长度
            salt
        版本要求
            参数选择需要依据实施时有效标准、平台能力和威胁模型
            不能把旧教程中的固定迭代次数当成长期安全值
        识别限制
            字段包含 salt 和长字符串不证明使用了某一种方案

    密码学随机性
        CSPRNG
            密码学安全伪随机数生成器用于生成不可预测的随机材料
        需要不可预测的值
            secret key
            某些签名方案的临时秘密
            CBC 等方案要求不可预测的 IV
        需要唯一的值
            GCM nonce
            CTR counter block
            某些协议序号
        唯一与不可预测不同
            计数器可以唯一但可预测
            随机值可以不可预测但仍存在碰撞概率
        错误来源
            通用非密码学随机函数
            时间戳直接作为秘密
            多进程或多设备重复计数器
            状态回滚后重复 nonce

    密钥生命周期
        生成
            使用符合方案要求的安全随机源或标准密钥生成算法
        导入
            确认编码、算法、长度和用途
        使用
            限制在声明用途，例如 encrypt、decrypt、sign、verify 或 derive
        存储
            根据密钥类型限制访问和导出
        轮换
            新旧密钥需要通过版本或 key id 区分
        撤销与销毁
            停止接受已撤销密钥产生的新数据
            按系统要求清除不再需要的秘密材料
        记录原则
            只记录生命周期状态和来源类别
            不把密钥值写入调试笔记、HAR、截图或日志

    密钥分离
        不同目的应使用不同密钥或由 KDF 派生的不同子密钥
        需要分离的用途可能包括
            encryption
            authentication
            client-to-server
            server-to-client
            不同协议版本
        原因
            不同算法对密钥的使用方式不同
            单一密钥跨用途复用会扩大泄露和设计错误影响
        观察要求
            相同文本值出现在多个 key 参数中是风险线索
            仅凭变量名相同不能证明底层密钥字节相同

    浏览器端秘密边界
        发送到浏览器的静态代码和静态配置可以被该浏览器使用者观察
        硬编码在前端 JavaScript 中的长期共享值不能被视为服务端独占秘密
        压缩、混淆和 Base64 不能赋予密钥保密性
        会话期间在浏览器中使用的秘密材料仍可能受运行环境和端点安全影响
        结论边界
            发现前端常量不等于获得修改或复用它的授权
            前端“签名”是否提供强客户端身份，需要结合密钥分发和服务端信任模型判断

    Web Crypto
        概念
            Web Crypto API 是浏览器提供的密码学接口集合
            它不是一种算法
        能力类别
            digest
            encrypt 和 decrypt
            sign 和 verify
            generateKey、importKey 和 exportKey
            deriveBits 和 deriveKey
            wrapKey 和 unwrapKey
            密码学随机数生成
        数据边界
            密码学操作处理字节缓冲区和 CryptoKey 等对象
            字符串必须先按明确字符编码转换为字节
        异步边界
            多数 subtle 密码学操作以 Promise 形式返回结果
            调用栈需要结合第 3 阶段的异步来源阅读
        支持范围
            算法和参数支持取决于浏览器与规范版本
            实施时需要核对当前浏览器官方文档

    CryptoKey
        概念
            CryptoKey 表示 Web Crypto 管理的密钥对象
        需要记录的属性类别
            type
            algorithm
            usages
            extractable
        type
            secret
            public
            private
        usages
            指定该对象允许的操作类别
            encrypt 与 decrypt、sign 与 verify、deriveKey 与 deriveBits 等用途不能混为一谈
        extractable
            表示 Web Crypto 是否允许通过相应接口导出密钥材料
            non-extractable 不等于密钥必然由硬件保护
        证据限制
            只看到 CryptoKey 对象不能确认上游字符串编码和协议封装

    Web Crypto 算法参数对象
        调用通常需要算法名称和参数对象
        同一算法家族的必要字段不同
            AES-CBC 需要 IV
            AES-CTR 需要 counter 和计数长度
            AES-GCM 需要 IV，并可包含 AAD 与 tag length
            RSA-OAEP 需要哈希等与密钥和方案匹配的参数
        Web Crypto RSA-OAEP 参数归属修正
            上面的 RSA-OAEP 句子描述完整方案需要匹配的参数，不表示每次调用都传入 hash 字段
            在 Web Crypto 中，hash 属于 RSA-OAEP 密钥的算法信息，并在生成或导入密钥时确定
            每次 encrypt 或 decrypt 使用的 RsaOaepParams 包含 name 和可选 label
            记录时从 CryptoKey.algorithm 读取 hash，不在每次调用参数对象中补写不存在的 hash 字段
        记录要求
            算法名称
            每个参数的类型与解码后字节长度
            CryptoKey.algorithm
            CryptoKey.usages
            输入和输出是 ArrayBuffer 还是某种 TypedArray 视图
        本阶段不调用这些接口，只学习参数分类

    CryptoJS
        概念
            CryptoJS 是第三方 JavaScript 密码学库名称
            它不是浏览器原生 Web Crypto
            它也不是一种算法
        数据类型
            CryptoJS 常使用 WordArray 表示二进制数据
            WordArray 与 Uint8Array 的内部表示和长度单位不同
        编码器
            Utf8
            Hex
            Base64
            其他版本提供的编码器
        参数边界
            原始 key 与 passphrase 字符串可能进入不同处理路径
            mode、padding、IV、salt 和输出格式可能由调用方式与版本决定
            不能依赖未核对版本的默认值
        记录要求
            库版本
            入口函数
            key 参数类型
            输入是字符串还是 WordArray
            mode、padding、IV 和 formatter 是否显式提供

    Web Crypto 与 CryptoJS 结果不一致
        不能先判断某一方“算法错误”
        需要逐项核对
            原始文本是否完全相同
            字符编码是否相同
            输入字节是否相同
            key 字节和 key 长度是否相同
            passphrase 是否触发了密钥派生
            mode 是否相同
            IV 或 nonce 是否相同
            padding 是否相同
            AAD 和 tag length 是否相同
            输出是否包含 salt、IV、nonce 或 tag
            Hex、Base64 与 Base64url 是否相同
        任一差异都可以产生不同结果
        第 5 阶段再使用这张清单分析具体签名输入

    输出封装
        密码学原语输出通常只是字节
        协议字段可能进一步组合
            version
            algorithm identifier
            key identifier
            salt
            IV 或 nonce
            wrapped key
            ciphertext
            tag
            signature
        组合方式
            固定位置拼接
            长度前缀
            JSON
            ASN.1 DER
            自定义二进制结构
        外层编码
            Hex
            Base64
            Base64url
            URL 编码
        判断限制
            字段总长度不等于原语输出长度
            必须先拆分封装和外层编码，再讨论候选算法

    常见长度关系
        普通哈希
            输出字节长度由算法固定
        HMAC
            完整标签长度通常与底层哈希输出相关，也可能按协议截断
        AES-CBC
            密文主体在 padding 后是 16 byte 的倍数
            字段还可能包含 IV 和外层编码
        AES-CTR
            密文主体通常与明文等长
            字段还可能包含 counter 或 nonce
        AES-GCM
            密文主体通常与明文等长
            另有 tag，并可能携带 nonce
        RSA
            密文或签名字节长度通常与模数大小相关
        椭圆曲线签名
            原始参数长度与 DER 编码后的可见长度可能不同
        结论
            长度关系适合检查候选是否自洽
            长度关系不适合单独确认算法

    熵与外观
        熵是对符号分布不确定性的统计量
        短字段的熵估计通常不稳定
        高熵外观可能来自
            密文
            压缩数据
            随机数
            摘要
            认证标签
            已编码二进制数据
        低熵或可读前缀也不能排除加密封装
            字段可能包含版本头
            nonce 或 IV 可能公开
            密文可能只占字段一部分
        禁止结论
            不使用固定熵阈值直接判定加密
            不使用“长度是 16 的倍数”直接判定 AES

    算法候选证据强度
        弱证据
            字段名包含 sign、token、hash、aes 或 rsa
            字段是 Hex 或 Base64
            字段长度符合某个常见输出
            字段看起来随机
        中等证据
            多次受控观察符合确定性或 nonce 变化规律
            解码后结构符合 IV、ciphertext、tag 的自洽长度关系
            调用链中出现相关库和参数对象
        强证据
            已授权源码明确调用具体原语并显示完整参数
            CryptoKey.algorithm、mode、padding、hash 和输入字节边界都得到记录
            公开协议规范与当前代码参数一致
        已验证结论
            后续阶段在相同字节和参数下得到可重复验证结果
            服务端或规范的验证行为与记录一致
        注意
            强证据仍可能只覆盖某个版本或某条分支
            结论必须绑定构建版本和采集编号

    密码学字段分类顺序
        第一步：记录字段位置
            URL 查询、请求头、Cookie、请求体或响应体
        第二步：记录外层表示
            原始文本长度
            字符集合
            Hex、Base64、Base64url、JSON 或未知
        第三步：记录解码后结构
            总字节长度
            是否有稳定前缀
            是否可拆出长度字段、IV、nonce、tag 或版本
        第四步：回到 Sources 调用链
            记录函数位置和库入口
            记录输入值类型和字节长度
            记录 key 关系但不记录 key 值
        第五步：记录完整参数
            hash
            mode
            padding
            IV、nonce 或 counter
            salt、AAD 和 tag length
        第六步：形成候选
            哈希
            MAC 或 HMAC
            对称加密
            AEAD
            公钥加密
            数字签名
            KDF 输出
            非密码学待分类字段
        第七步：保留替代解释
            每个候选都写出尚未满足的必要条件
            不在本阶段生成或验证真实字段

    常见错误
        把摘要称为密文
            问题
                哈希没有解密密钥或逆向解密过程
            修正
                根据输入、输出和密钥关系分类
        把 HMAC 当成 SHA-256
            问题
                HMAC 还有共享密钥和独立构造
            修正
                明确记录 key 与 message 两类输入
        把 secret 拼接哈希称为 HMAC
            问题
                简单拼接不等于标准 HMAC 构造
            修正
                只有代码或规范显示 HMAC 才使用该名称
        把加密当成完整性保护
            问题
                ECB、CBC 和 CTR 本身不提供认证
            修正
                检查是否有 MAC、tag 或 AEAD 方案
        把 IV 当成密钥
            问题
                IV 通常公开，但有模式特定的唯一性或不可预测性要求
            修正
                分别记录 key 与 IV 的来源、长度和用途
        对所有 nonce 要求随机
            问题
                有些方案重点要求唯一，计数器也可满足
            修正
                按具体方案记录唯一性和不可预测性要求
        认为 salt 必须保密
            问题
                salt 通常作为公开的每实例不同输入
            修正
                保密的是密码、pepper 或密钥，不是普通 salt
        把 Base64 的 = 当成加密 padding
            问题
                Base64 补位和分组密码 padding 属于不同层
            修正
                先分离外层文本编码与内部密码学结构
        把 AES-256 的 256 当成分组大小
            问题
                256 表示密钥大小，AES 分组仍为 128 bit
            修正
                分别记录 block size 和 key size
        只写 AES 不写模式
            问题
                ECB、CBC、CTR 和 GCM 的参数与安全性质不同
            修正
                同时记录 mode、IV 或 nonce、padding 和 tag
        把 GCM tag 当成密文尾部必然固定结构
            问题
                协议可以分开、拼接或重新封装 tag
            修正
                从调用参数和封装解析确认位置
        GCM 重复 nonce
            问题
                同一密钥下重复 nonce 会严重破坏安全性
            修正
                记录 nonce 生成域、持久状态和唯一性保证
        把 RSA 签名称为私钥加密
            问题
                签名有独立的编码、哈希和验证方案
            修正
                使用完整 Sign、Verify 和 scheme 术语
        使用 RSA 直接处理任意长消息
            问题
                输入长度受模数和编码开销限制
            修正
                识别标准混合加密或密钥封装结构
        把 ECDH 当成 ECDSA
            问题
                一个用于密钥协商，一个用于数字签名
            修正
                根据 key usages 和调用操作分类
        直接哈希密码
            问题
                快速哈希没有专用密码处理的成本参数
            修正
                识别 salt、工作因子和密码派生方案
        把 Web Crypto 当成算法
            问题
                Web Crypto 是接口集合
            修正
                记录具体算法名称和参数对象
        把 CryptoJS 默认值当成协议
            问题
                默认行为受版本、入口和 key 类型影响
            修正
                记录版本并确认所有隐式参数
        用长度确认算法
            问题
                截断、封装和外层编码会产生相同长度
            修正
                长度只用于检查候选自洽性
        用熵确认密文
            问题
                摘要、压缩和随机数也可能呈现高熵
            修正
                使用调用、参数和输入输出关系作为证据
        忽略密钥管理
            问题
                算法正确不代表密钥生成、存储、轮换和用途正确
            修正
                把密钥生命周期作为机制记录的一部分
